# Дашборд показателей ВМР · МСК

Единственный документ по дашборду: как он устроен, откуда берёт данные, как считает показатели и как его запускать. Предыдущие файлы (`КАК-РЕАЛИЗОВАН-ПРОЕКТ.md`, `сеанс-*.md`) слиты сюда.

Ориентир по составу блоков и формулам — ТЗ «Дашборд ВМР МСК» (извлечение: `tools/_tz-dashboard-extract.txt`).

---

## Коротко

Flask-приложение на три файла логики: `app.py` отдаёт HTML и один JSON-эндпоинт, `db.py` держит все SQL-запросы и расчёты, фронтенд на Chart.js рисует плитки и графики. Данные берутся **живыми запросами напрямую к SQL-копиям баз 1С** — без OData, без ночной витрины и без участия MCP в рантайме.

```
[Браузер] ──fetch /api/data?from=&to=──► [Flask app.py]
                                              │
                                      build_dashboard() в db.py
                                              │
                        ┌─────────────────────┴──────────────────┐
                  pymssql → msk_uat                      pymssql → msk_buh
            (смены, отгрузки, тюки, взвешивания)     (реализации, цены, покупатели)
                        └─────────────────────┬──────────────────┘
                                              ▼
                                   один JSON со всеми блоками
```

MCP-сервер `odines` использовался **только на этапе разработки** — чтобы через `ПолучитьСтруктуруХраненияБазыДанных(, Истина)` узнать, в каких физических таблицах (`_Document18335`, `_Fld18353` и т.п.) лежат объекты 1С. Эти имена зафиксированы в `db.py`. Если MCP выключить, дашборд продолжит работать, пока доступен SQL Server.

## Запуск

```powershell
cd C:\vs\dashboard
pip install -r requirements.txt
# пароль SQL — в .env (SQL_PASSWORD=...), шаблон — .env.example
python app.py
# http://127.0.0.1:5050
```

Зависимости: `flask`, `pymssql`, `python-dotenv`. Драйвер именно `pymssql` — «ODBC Driver 17/18 for SQL Server» на машине может отсутствовать.

Конфигурация целиком в `.env` (пароль в git не коммитится):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SQL_SERVER_UAT` | `192.168.80.10` | сервер УАТ |
| `SQL_DATABASE_UAT` | `msk_uat` | база УАТ |
| `SQL_SERVER_BUH` | `192.168.80.10` | сервер БП |
| `SQL_DATABASE_BUH` | `msk_buh` | база БП |
| `SQL_USER` | `user1c` | логин SQL |

Сервер приложений 1С (`192.168.80.15`) для SQL **не годится**: порты 1433/1434 там закрыты. Обе базы живут на `192.168.80.10`, на одном инстансе — поэтому продажи читаются одним кросс-БД запросом, без linked server.

## API

### `GET /`

Рендер страницы. В поля дат подставляется **текущий календарный месяц**.

### `GET /api/data?from=YYYY-MM-DD&to=YYYY-MM-DD`

Один запрос отдаёт сразу все блоки:

```json
{
  "ok": true, "from": "...", "to": "...",
  "kpis":       { "production_t", "shift_count", "shipped_t", "trip_count",
                  "sold_rub", "sold_tons", "shrink_pct", "shrink_kg", "shrink_rub" },
  "selection":  { "days", "arrived_t", "selected_t", "pct" },
  "production": { "days", "brigades", "workshops", "shift_count", "total_kg", "note" },
  "shrinkage":  { "trips", "by_fraction", "total", "median_pct", "anomalies" },
  "warehouse":  { "as_of", "rows", "total_kg", "total_rub" },
  "prices":     { "months", "series" },
  "sales":      { "by_fraction", "buyers", "total_rub", "total_tons", "concentration" },
  "sales_error": null,
  "rows":       [ ...строки смен... ]
}
```

Поведение по ошибкам: неверный формат даты или `from > to` → `400` с `{"ok": false, "error": ...}`; любое исключение внутри `build_dashboard()` → `500`. Отдельно обработаны продажи: если недоступна БП, остальные блоки всё равно вернутся, а текст ошибки придёт в `sales_error`.

Две сквозные договорённости:

- граница «по» **включительная** — в SQL уходит `date_to + 1 день` как exclusive;
- даты 1С в SQL лежат со смещением **+2000 лет**, поэтому везде `DATEADD(year, -2000, _Date_Time)`.

## Поток одного запроса

`build_dashboard(date_from, date_to)` в `db.py`:

1. `fetch_shifts` — смены с ТЧ «Товары» (УАТ);
2. `fetch_shipments` — отгрузки с ТЧ (УАТ);
3. `fetch_selection` — приехавшее ТКО из регистра взвешиваний против отобранного по сменам (УАТ);
4. `fetch_warehouse` — тюки со статусом «На складе», без привязки к периоду (УАТ);
5. `fetch_sales` — дважды: за выбранный период и за последние 12 месяцев (кросс-БД БП + УАТ). Годовая выборка нужна для графика цен и для «последней цены» склада;
6. сборка блоков: `_build_production`, `_build_shrinkage`, `_build_warehouse`, `_build_sales`, `_build_prices`;
7. расчёт KPI и возврат единого словаря.

Соединение открывается на каждый запрос через контекстный менеджер `connect()` (`login_timeout=10`, `timeout=90`, `charset="utf8"`), пул не используется. Значения из `pymssql` проходят через `_serialize`: `Decimal` → `float`, даты → ISO-строка, `bytes` → UTF-8.

### Связка номенклатуры БП ↔ УАТ

Прямой join по `_IDRRef` между базами невозможен — справочники независимы. Работает связка через реквизит **`уатВидГруза`** номенклатуры УАТ: из наименования БП убирается префикс «Вторичные ресурсы, извлеченные при сортировке твердых коммунальных отходов» и скобки, остаток нормализуется (нижний регистр, `ё` → `е`, пробелы вокруг запятой) и сравнивается с наименованием вида груза.

Всё это один SQL-запрос `SALES_VMR_QUERY` (автономная копия — `tools/sales-vmr-buh-uat.sql`). Внутри:

- берутся только позиции УАТ из группы-папки **«ВМР»** (`_ParentIDRRef`, `_Folder = 0x00` — это группа), поэтому провода, масла и щепа древесная в выручку не попадают;
- `CROSS APPLY` с ранжированием: точное совпадение имеет приоритет над совпадением по началу строки, за счёт которого «ПЭТ микс 4 цвета» садится на вид «ПЭТ микс»; при нескольких вариантах берётся самое длинное совпадение.

Join через «вид номенклатуры» УАТ (`_Reference48` / `_Fld5881RRef`) пробовали — не сработало, имена не совпадают с продажами БП.

Известные частные случаи сопоставления:

|---|---|---|
| стеклобой микс | стеклобой микс | Стекло |
| ПЭТ бело-голубой | ПЭТ бело-голубой | ПЭТ бело-голубой |
| ПЭТ микс | ПЭТ микс | ПЭТ Коричнево-зелёный МИКС |

## Что считается и как

### Фильтр периода

Строка сверху закреплена при прокрутке: слева меню разделов, справа пресеты **Неделя** (пн–вс), **Месяц**, **Квартал**, **Год**, поле дат «с — по» и кнопка обновления. Пресет сразу пересчитывает даты и грузит данные. Ручная правка дат снимает активный пресет и применяется сразу, без отдельной кнопки. По умолчанию — текущий календарный месяц. Период управляет всеми блоками, кроме «Склада».

### KPI (4 плитки)

| Плитка | Значение | Расчёт |
|---|---|---|
| Выработка | тонны + число смен | сумма количеств строк смен / 1000 |
| Вывезено | тонны + рейсы | сумма весов по весам, вес берётся один раз на документ |
| Продано | ₽ + тонны | сумма по реализациям БП за период |
| Усушка | % и кг | `(вес тюков − вес по весам) / вес тюков × 100` |

Нюансы, которые легко принять за ошибку:

- **число смен ≠ числу документов.** Смены, у которых все строки с бирками **БПВ** и **ББА**, не считаются: это автоматические смены под россыпь, бригада в них не работала. Тонны при этом не меняются — вес россыпи в выработке остаётся. Счётчик реализован дважды: `_worked_shift_ids` в `db.py` и `realShiftCount` в `dashboard.js`.
- **усушка в рублях — грубая оценка:** потерянные тонны × средняя цена корзины продаж периода, а не цена конкретной фракции.
- «Продано» и «Вывезено» расходятся штатно: реализацию оформляют позже вывоза.

Под плитками две плашки: **«Склад сейчас»** (тонны и ₽ из блока «Склад») и **«Средняя цена продажи»** = продано ₽ / продано т за период.

### Процент отбора

Приехавшее ТКО (нетто из регистра взвешиваний, вид отходов «ТКО») против отобранного по сменам, по дням периода плюс итог за период. `FULL JOIN` по дням, чтобы день без одной из сторон не выпадал.

Столбик дня разделён на **тюки** и **россыпь**: россыпь по дням считается во фронте из строк смен (`rows`) по списку россыпных фракций. Россыпь попадает в смены в день отгрузки, поэтому без разделения день отгрузки стекла выглядел бы рекордом сортировки.

### Склад

Остаток **на сегодня**, период не влияет (бейдж в заголовке). Только тюки со статусом «На складе». Цена ₽/т по каждой позиции — из её **последнего** проведённого документа реализации в БП (`_last_prices_from_sales`), а не средняя за период; если в документе несколько строк одной номенклатуры, цена = сумма этих строк ÷ количество. Цена ищется по имени номенклатуры УАТ, затем по её виду груза. Позиция без пары в БП получает цену 0 — так, например, макулатура даёт нулевую оценку; на странице у такой позиции вместо цены и стоимости написано «нет продаж» (AKEA-778).

### Производство

**Сравнение бригад в тоннах за смену** (без россыпи и автоматических смен БПВ/ББА): у бригад за период разное число смен, поэтому общие тонны сравнивать некорректно. Под графиком — на сколько процентов одна бригада выше другой. Рядом таблица по цехам (кг, доля, итог, число смен). Цеха в данных: «МСК новый», «МСК старый».

### Усушка

Потеря рейса делится между фракциями пропорционально весу тюков по биркам:

- коэффициент рейса = вес по весам / сумма весов тюков;
- вес фракции по весам = её вес по биркам × коэффициент;
- усушка фракции = бирки − её вес по весам.

Поле «Расхождение» из 1С **не используется** (ТЗ §8.3): оно пишется один раз при загрузке весов и не пересчитывается. Отгрузка без номера документа весов и с нулевым весом в усушку не входит — иначе это выглядело бы как 100% потери; в «Вывезено» такие рейсы остаются. Рейсы с отклонением больше 15% помечаются как аномальные и исключаются из медианы (пунктир на графике). Россыпь в расчёте остаётся с усушкой 0%: вес бирок равен весу по весам. В таблице «Усушка по фракциям» россыпь не показывается — при поступлении она не взвешивается.

### Цены

Индекс помесячно за последние 12 месяцев, первый месяц ряда = 100. Средневзвешенная цена месяца = `SUM(сумма) / SUM(количество)`. В ряды попадают только позиции, которые продавались в выбранном периоде; ряды с наибольшим числом заполненных точек идут первыми.

Рядом с графиком таблица **«Последняя цена»**: средняя цена в последнем месяце, когда фракцию продавали, и её изменение к первому месяцу ряда.

### Продажи

Выручка по фракциям (подписи — номенклатура УАТ) и структура покупателей в ₽ с долями. Если доля одного контрагента превышает **50%**, в блоке появляется предупреждение о концентрации.

Цвета фракций заданы один раз в `FRACTION_COLORS` (`db.py`) и одинаковы во всех блоках (ТЗ §9); название сравнивается без учёта регистра и лишних пробелов (в 1С встречаются двойные и неразрывные), незнакомая фракция получает нейтральный цвет.

## Особенности тестовых данных

Это свойства копии базы, а не ошибки дашборда:

- **наполнение периодов плавает.** Если KPI нулевые — сначала проверьте выбранный период, а не подключение: при успешном запросе API отдаёт `"ok": true`. На 18.09.2026 смены были примерно за 31.07–14.09.2026, а май–июнь пустовали; в более ранних копиях было наоборот. Продажи БП при этом могут быть ненулевыми даже при пустой выработке.
- парные смены с разницей в 1 секунду и одинаковым `ИтогоТКО`, но разными подразделениями — в разрезе цехов похоже на дублирование;
- дробные количества там, где ожидаются целые (Картон 450,004);
- в остатках встречаются аномальные бирки: почти весь объём стекла на одной бирке, алюминиевая банка на порядок тяжелее средней.

| Контрольные цифры авг. 2026 | зависят от наполнения копии |

## Приложение: доступ к базе 1С для разведки

Рантайму дашборда это не нужно — только чтобы уточнить структуру данных или прогнать отчёт.

MCP-сервер `odines` («1C MCP Toolkit (Native)») на `http://192.168.80.15:6003/mcp`, транспорт `http`, заголовок `Authorization: Bearer <токен>` — префикс `Bearer` обязателен, голый токен даёт 401. Запись хранится в `~/.claude.json` → `projects["C:/vs"].mcpServers.odines`. Регистрация заново (обновления на месте нет, сначала `remove`):

```powershell
claude mcp remove odines -s local
claude mcp add --transport http odines http://192.168.80.15:6003/mcp --header "Authorization: Bearer <токен>"
```

URL обязателен со схемой: без `http://` запись создастся, но `claude mcp list` упадёт с «'url' is not a valid URL».

Инструменты: `execute_query`, `execute_code`, `get_metadata`, `get_event_log`, `get_object_by_link`, `get_link_of_object`, `find_references_to_object`, `get_access_rights`, `get_bsl_syntax_help`, `get_screenshot`, `restart_1c_session`, `close_1c_session`. Прикладные объекты лежат в **`Расширение1`** — для `get_metadata` нужен `extension_name: "Расширение1"`.

Бывает, что `claude mcp list` показывает `✔ Connected`, а инструментов `mcp__odines__*` в сессии нет. Обычно лечится перезапуском клиента; пока сессия жива, обходной путь — `tools/mcp-odines.ps1`, он ходит на тот же эндпоинт по JSON-RPC, беря URL и токен из `~/.claude.json`:

```powershell
.\tools\mcp-odines.ps1 -Method tools/list
.\tools\mcp-odines.ps1 -Method tools/call -ParamsFile args.json -Out result.txt
.\tools\mcp-odines.ps1 -Method tools/list -Token <токен> [-Url http://192.168.80.15:6003/mcp]
```

Грабли, уже учтённые в скрипте (не переписывайте обратно): ответ приходит как `text/event-stream`, значимые строки начинаются с `data:`; PowerShell 5.1 декодирует такой поток как ISO-8859-1 и портит кириллицу, поэтому читается `RawContentStream` с ручным UTF-8; `Invoke-WebRequest` нужен с `-UseBasicParsing`; `~/.claude.json` не разбирается через `ConvertFrom-Json` из-за дублирующихся ключей `c:/vs` и `C:/vs`.

Отдельно про скрипты в `tools/`: **файл `.ps1` с кириллицей должен быть в UTF-8 с BOM**, иначе PowerShell 5.1 читает его как Windows-1251 и сыплет «Unexpected token» — выглядит как синтаксическая ошибка, хотя синтаксис цел. После записи файла без BOM:

```powershell
$p='tools\имя.ps1'; $t=[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)
[IO.File]::WriteAllText($p,$t,(New-Object Text.UTF8Encoding($true)))
```

Отчёты СКД (`ВыработкаПоБригадам` и др.) запускаются через `execute_code` в контексте `server` ручной компоновкой — модуль отчёта при этом не отрабатывает. У `ВыработкаПоБригадам` задаётся параметр `Период` (тип `СтандартныйПериод`), а `НачДата` / `КонДата` вычисляются из него и установке не поддаются; `Бригада` принимает `СписокЗначений`; `ВЦелом` переключает разрез по бригадам. У объекта параметра СКД нет свойства `Тип` — есть `ТипЗначения` и `ДоступенСписокЗначений`.
